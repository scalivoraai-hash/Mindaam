# ADR-0025: shared surfaces and bounded operator control

The existing `/super-admin` route and operations router remain authoritative. `theme.css`, imported after the existing layout stylesheets, owns semantic light/dark tokens; the former conflicting root definitions and forced glass background are removed. Immersive world tools explicitly scope dark tokens, while content panels use white surfaces. The approved logo, renderer, media lifecycle and geography are unchanged. Only the duplicate floating rental shortcut is removed.

User reads are role-gated and paginated. Detail views expose administrative identity, ledger, event/access/payment records and social counts, not private messages or device coordinates. Fresh authenticated presence means a non-suspended user with a valid session and an observation within 90 seconds; multiple sessions do not duplicate a user. Activity history contains only recorded observations.

Adjustments append through the existing immutable ledger service. Promotional/support PC never become purchased PC. Single-operator limits default to 1,000 PC, 5,000 XP and 20 actions per rolling 24 hours; bounded policy changes are audited. Above-limit requests use the additive `fv28_operator_reviews` table and a different eligible Super Admin must approve. Pending requests issue nothing. Review approval has a seven-day validity window, a 20/day approver cap, stable ledger idempotency and audited before/after balances. Privileged accounts cannot receive these grants. Existing balance and payment recovery policies still apply.

Finance aggregates the full selected checkout-creation cohort, while detail rows are bounded. GBP payments/refunds are separate from PC circulation and XP. Subscription cash totals, provider fees and bank settlement remain explicitly unavailable because the current records do not establish them. Subscription catalogue management reuses the existing billing API and immutable plan snapshots; it does not create Stripe products/prices or alter settled purchases.

Owner bootstrap continues to require securely configured `SUPER_ADMIN_EMAIL`, `SUPER_ADMIN_USERNAME` and `SUPER_ADMIN_INITIAL_PASSWORD`. It refuses implicit elevation of existing accounts and requires an initial password change. No owner credential is embedded in code. MFA is not integrated: production promotion remains blocked pending secure MFA integration and owner security review. Staging acceptance still requires actual deployment credentials, provider readiness and an approved funded QA host; local fixtures are not evidence of those prerequisites.
