# ADR 0019 — Preview-referenced movement and controlled camera

Continue release a97d63e on the existing application and Railway service. Scope is movement/camera only. No schema, pricing, ledger, access, authentication, media or event lifecycle change.

The public preview has one movement pace, not separate walk/run states: 1.5 virtual metres per 120 ms input tick. The authenticated server incorrectly used that pace as RUN and divided it by 1.875 for WALK. Default held input never selected run. Local production-build measurements on the same clear mapped Whitehouse road were 12.90 m/s preview, 6.68 walk and 12.52 explicit run. They do not support a 7–10× multiplier. Preview source, tick and step remain intact.

The shared contract now uses 12.5 m/s walk and 23.4375 m/s run, with the existing 0.24 second server acceleration. Held keyboard or substantial joystick input selects run after 350 ms; light joystick input stays walking. Release, input loss and location changes reset the hold. Existing explicit controls remain optional. Server authority, swept collisions, timestamp ordering, input rate limits and bounded elapsed time remain unchanged. No client position or per-frame API call is introduced. Observed local acknowledgements and remote final positions agree. A cold CI trial also exposed overlapping HTTP fallback batches while world entry/socket establishment was still pending: acknowledgements were delayed 0.47–1.66 seconds and the bounded elapsed-time integrator reduced effective travel. The world connection now waits for entry to finish, gives the socket its existing five-second grace, and permits only one fallback batch in flight. The batch lock waits for every read to settle even if one fails early; a slow remaining request cannot overlap the next batch. This removes startup request pile-up without weakening server speed, collision or backlog safeguards. A network interruption exceeding existing safety bounds can still interrupt movement; this release does not promise offline locomotion.

Shared rental speed minima are bike 28, e-bike 31, scooter 34 and car 40 m/s; acceleration reaches the floor in two seconds. This preserves walk < run < bike < car < bus (46 m/s). Existing administrator values above these minima remain. Apply the calibration when presenting settings and driving existing leases; do not rewrite commercial lease snapshots or prices. The local and remote avatar use the same continuous run blend, with bounded cadence; preview/NPC animation keeps its previous profile.

Authenticated look sensitivity is 0.0012 rad/pixel mouse and 0.0016 touch, versus preview's preserved 0.0022/0.0028. Existing exponential angular damping remains. Canvas-owned pointer tracking separates drag and pinch; a remaining pinch contact cannot suddenly become a drag. UI and joystick contacts are excluded. Authenticated zoom limits are 6–38 m outdoors and 6–10 m indoors. Interior orbit uses an angle-independent pivot with a complete circle inside room bounds; it no longer rotates a six-metre focus offset or shortens its radius against auditorium scenery. Pitch is bounded by room height. The camera uses the damped spherical pose directly, removing chord-cutting from the second Cartesian interpolation. Exterior obstruction protection is retained; an obstacle may still shorten the effective exterior camera radius without changing explicit zoom state.

All active/future destinations and venue instances consume these shared modules. Validation uses disposable local accounts and mapped roads, a production Next build, actual authenticated WebSocket input, and rendered WebGL view matrices. This is not physical iOS/Android/Safari or production-account acceptance. Exact release CI and deployment evidence belong in MOVEMENT_CAMERA_VALIDATION_2026-10-01.md.
