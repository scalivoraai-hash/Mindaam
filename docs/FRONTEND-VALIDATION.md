# Frontend completion and validation

The Next.js consumer, merchant and admin views share form/list components outside route modules, preserving Next route export requirements. Tenant management uses `/businesses/{id}/manage`; public storefront queries remain verified-only. Merchant state uses the backend `status` field. Store visits are recorded on actual authenticated store openings, and new-business creation selects the new record.

The WebGL district now renders the same plus-shaped 28-metre-wide street region accepted by the authoritative movement API. Keyboard movement is renderer-independent, retaining WASD and arrow keys in the SVG fallback. Coordinates remain simulated virtual metres.

Recurring billing includes consumer plans, business plans, a Stripe catalogue editor for administrators, and provider-hosted cancellation links. `/wallet` exists for payment return navigation. No payment return query grants rewards or entitlements; balances are fetched from the server.

The install manifest and icons are available. A narrow service worker caches only public icons and manifest assets. Account routes, API responses, credentials and gameplay are never cached. The application requires a live backend to play; installation does not imply offline gameplay.

Validation: optimized Next.js build and TypeScript checks run from the root. Browser interaction, backend permission/economy integration and external-provider gates are separate tests; compilation alone is not a production certification. Current UI deliberately retains its local-alpha and simulated-city labels.
